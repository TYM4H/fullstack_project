# Парсер афиш и событий

Fullstack-проект для создания, публикации и просмотра событий.

## Назначение приложения

Приложение предназначено для создания событий на основе изображений афиш и баннеров. Организатор загружает изображение, а ИИ в будущем будет извлекать из него название события, дату, время, место проведения и описание. Полученные данные можно будет проверить и отредактировать перед публикацией.

Сейчас доступны создание событий, модерация, поиск по афише и оформление билетов. Распознавание афиш и выпуск действующих билетов с QR-кодами планируются на следующих этапах.

## Пользователи приложения

- **Организатор** — загружает афишу, проверяет данные и создаёт событие.
- **Модератор** — проверяет созданные события и принимает решение о публикации.
- **Посетитель** — просматривает опубликованные события и получает билет.

В текущей версии все экраны доступны без авторизации. Роли описывают пользовательские сценарии; разграничение прав пока не реализовано.

## Основные пользовательские сценарии

1. Посетитель ищет опубликованные события по названию, описанию или площадке, фильтрует по категории и открывает подробную информацию.
2. Организатор добавляет афишу, заполняет форму и отправляет событие на модерацию.
3. Модератор одобряет событие или отклоняет его с указанием причины. Одобренные события появляются в общей афише.
4. Посетитель получает билет на выбранное событие, скачивает его в текстовом формате или печатает. Повторное оформление возвращает тот же билет в текущем браузере.

Распознавание изображений, авторизация, оплата и проверка билетов на входе пока не реализованы. Backend поддерживает хранение мест и событий в PostgreSQL. Frontend работает независимо от API: использует начальный набор событий и сохраняет изменения в `localStorage` текущего браузера.

## Основные экраны

- Главная страница со списком событий.
- Страница выбранного события.
- Страница создания события.
- Страница модерации.
- Страница билета.
- Страница 404 для неизвестного адреса.

### Frontend

- React;

## Структура проекта

```text
backend/
├── app/
│   ├── api/routes/    # маршруты FastAPI
│   ├── core/          # конфигурация приложения
│   ├── crud/          # операции создания, чтения, изменения и удаления
│   ├── db/            # подключение, сессии и создание таблиц
│   ├── models/        # модели таблиц SQLAlchemy
│   ├── schemas/       # схемы запросов и ответов Pydantic
│   └── main.py        # точка входа backend
├── .env.example       # пример переменных окружения без секретов
└── requirements.txt   # зависимости Python

src/
├── app/            # маршруты, провайдер состояния, общие стили
├── pages/          # композиция экранов приложения
├── features/       # пользовательские действия
│   ├── create-event/     # форма, валидация и загрузка афиши
│   ├── filter-events/    # поиск и категории
│   ├── moderate-event/   # одобрение и отклонение
│   └── issue-ticket/     # оформление билета
├── entities/       # предметные данные и их представление
│   ├── event/      # типы, начальные данные, репозиторий, контекст, карточка
│   └── ticket/     # тип билета
├── shared/         # общие компоненты, форматирование дат и ошибок
└── main.tsx        # точка запуска React

tests/
└── frontend.mjs    # браузерные проверки пользовательских сценариев
```

Используется упрощённая структура на основе Feature-Sliced Design. `app` собирает
приложение, `pages` компонуют экраны, `features` реализуют действия пользователя,
`entities` описывают события и билеты, `shared` содержит код без привязки к
предметной области. Нижние слои не импортируют страницы и пользовательские
действия. Полный набор правил FSD не применяется: связанное хранение событий
и билетов находится в одном локальном репозитории.

`EventsProvider` хранит общее состояние событий и билетов в React Context.
Страницы и действия получают его через `useEvents`. Репозиторий отвечает за
чтение, проверку формата и запись в браузерное хранилище; компоненты не обращаются
к `localStorage` напрямую. Форматирование дат и отображение загрузки, ошибок
и пустых результатов вынесены в общие модули.

## Поведение frontend

- Поля формы управляются React-состоянием. Проверяются обязательность, длина
  текста, категория, существование даты и начало события в будущем.
- Время вводится и отображается по Москве (UTC+3), хранится в ISO 8601.
- Афиша необязательна. Поддерживаются JPG, PNG и WebP до 2 МБ, выбор файла,
  перетаскивание, предпросмотр, замена и удаление. Проверяются тип, размер
  и возможность декодирования изображения.
- События имеют статусы `pending`, `published` и `rejected`. Публичная афиша
  показывает только `published`; статистика модерации вычисляется из данных.
- Поисковый запрос и категория сохраняются в параметрах URL.
- Загрузка, ошибка и пустой результат отображаются отдельно. При ошибке
  доступна повторная загрузка.
- Кнопки отправки блокируются на время операции. При ошибке сохранения форма
  сохраняет введённые значения, а интерфейс показывает причину ошибки.
- Страницы и карточки появляются с коротким CSS-переходом. Учитывается
  системная настройка `prefers-reduced-motion`.
- Страницы создания, модерации и билета загружаются по требованию через
  `React.lazy` и `Suspense`. Все маршруты предыдущей версии сохранены.

### Локальные данные и ограничения

Ключ хранилища — `afisha:demo:v1`. При отсутствии сохранённых данных используются
пять примеров: три опубликованных события и два ожидающих проверки. Операции
асинхронные, с искусственной задержкой 400 мс для отображения состояния загрузки.
Изменения и билеты сохраняются после перезагрузки страницы.

Данные относятся к конкретному origin: `localhost:5173` и `127.0.0.1:5173`
имеют разные хранилища. Они не синхронизируются между браузерами, устройствами
и открытыми вкладками. Очистка данных сайта удаляет локальные события и билеты.
Повреждённое или недоступное хранилище вызывает понятную ошибку; автоматического
удаления пользовательских данных нет. Объём хранения ограничен браузером.

Оплата и проверка билетов на входе не подключены, действующий QR-код не создаётся.
Frontend-модель пока отличается от серверной: место хранится текстом,
используются строковые идентификаторы и три статуса модерации. Для интеграции
с API потребуется согласовать эти поля с `venue_id`, числовыми идентификаторами
и `is_published`, а также добавить серверную модель билета.

## Маршруты frontend

| Адрес                   | Страница                                                            |
| ----------------------- | ------------------------------------------------------------------- |
| `/`                     | Главная страница                                                    |
| `/events/:id`           | Страница события                                                    |

## Модель данных

В backend используются две связанные сущности:

```text
Venue (1) ──────── (*) Event
```

Одно место проведения может быть связано с несколькими событиями. Каждое
событие обязательно относится к одному месту.

### Таблица `venues`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | integer | Первичный ключ |
| `name` | varchar(200) | Название места |
| `address` | varchar(300) | Адрес |

### Таблица `events`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | integer | Первичный ключ |
| `title` | varchar(200) | Название события |
| `starts_at` | timestamp with time zone | Дата и время начала |
| `category` | varchar(100) | Категория |
| `description` | text | Описание |
| `is_published` | boolean | Признак публикации |
| `venue_id` | integer | Внешний ключ на `venues.id` |

Связь обеспечивается внешним ключом `events.venue_id → venues.id`. Удалить
место, на которое ссылается событие, нельзя: API вернёт статус `409 Conflict`.

## Подготовка PostgreSQL

Для работы backend должны быть установлены Python и PostgreSQL. Проверить их
можно командами:

```bash
python3 --version
psql --version
```

Создайте базу данных:

```bash
createdb events_db
```

Если команда `createdb` недоступна, базу можно создать через `psql`:

```sql
CREATE DATABASE events_db;
```

## Настройка backend

Перейдите в каталог backend, создайте виртуальное окружение и установите
зависимости:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Создайте локальный файл настроек из примера:

```bash
cp .env.example .env
```

Укажите в `backend/.env` параметры своего PostgreSQL:

```env
APP_NAME=Events API
DATABASE_URL=postgresql+psycopg://your_user:your_password@localhost:5432/events_db
```

Если локальный PostgreSQL не требует пароль, его можно убрать из адреса:

```env
DATABASE_URL=postgresql+psycopg://your_user@localhost:5432/events_db
```

Файл `.env` содержит локальные настройки и исключён из Git. В репозитории
хранится только безопасный шаблон `.env.example`.

## Запуск backend

Из каталога `backend` с активированным виртуальным окружением выполните:

```bash
uvicorn app.main:app --reload
```

После запуска доступны:

- API: `http://127.0.0.1:8000`;
- Swagger UI: `http://127.0.0.1:8000/docs`;
- ReDoc: `http://127.0.0.1:8000/redoc`;
- проверка сервера: `http://127.0.0.1:8000/health`.

При запуске вызывается `Base.metadata.create_all()`. Метод создаёт отсутствующие
таблицы `venues` и `events`, но не удаляет существующие таблицы и данные.
Alembic в этой лабораторной работе не используется.

Проверить создание таблиц можно командой:

```bash
psql events_db -c '\dt'
```

## Маршруты backend

| Метод | Адрес | Назначение | Успешный статус |
| --- | --- | --- | --- |
| `GET` | `/health` | Проверить работу сервера | `200` |
| `POST` | `/venues` | Создать место | `201` |
| `GET` | `/venues` | Получить список мест | `200` |
| `GET` | `/venues/{id}` | Получить место | `200` |
| `PATCH` | `/venues/{id}` | Частично изменить место | `200` |
| `DELETE` | `/venues/{id}` | Удалить место | `204` |
| `POST` | `/events` | Создать событие | `201` |
| `GET` | `/events` | Получить список событий | `200` |
| `GET` | `/events/{id}` | Получить событие вместе с местом | `200` |
| `PATCH` | `/events/{id}` | Частично изменить событие | `200` |
| `DELETE` | `/events/{id}` | Удалить событие | `204` |

Для списков поддерживаются параметры пагинации `offset` и `limit`. Значение
`limit` должно находиться в диапазоне от 1 до 100.

### Пример создания места

```bash
curl -X POST http://127.0.0.1:8000/venues \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Городской парк",
    "address": "Москва, Парковая улица, 1"
  }'
```

### Пример создания события

В `venue_id` укажите идентификатор места, полученный в предыдущем запросе:

```bash
curl -X POST http://127.0.0.1:8000/events \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Живая музыка",
    "starts_at": "2026-07-12T19:00:00+03:00",
    "category": "Концерты",
    "description": "Концерт живой музыки в городском парке",
    "venue_id": 1
  }'
```

Поле `starts_at` передаётся в формате ISO 8601. Например,
`2026-07-12T19:00:00+03:00` содержит дату, время и часовой пояс.

### Ошибки API

- `404 Not Found` — место или событие не существует;
- `409 Conflict` — место нельзя удалить, пока с ним связаны события;
- `422 Unprocessable Content` — запрос не прошёл Pydantic-валидацию.

## Запуск frontend

Для работы нужны Node.js 24 LTS и npm. Backend для текущего режима frontend запускать не требуется.

```bash
npm ci
npm run dev
```

После запуска Vite покажет адрес, обычно `http://localhost:5173`. Его нужно открыть в браузере.

## Проверка frontend

Проверить сборку приложения можно командой:

```bash
npm run build
```

Проверить код линтером можно командой:

```bash
npm run lint
```

Браузерные проверки используют Playwright. Перед первым запуском установите
тестовый браузер:

```bash
npx playwright install chromium
```

Запустите приложение в одном терминале, затем проверки в другом:

```bash
npm run dev -- --host 127.0.0.1
```

```bash
npm run test:e2e
```

По умолчанию тесты обращаются к `http://127.0.0.1:5173`. Переменная `BASE_URL`
позволяет изменить адрес, а `CHROME_PATH` — использовать установленный Chrome.
Тесты работают в отдельном браузерном контексте и не изменяют данные обычного
профиля пользователя.

Проверяются поиск и категории, URL-фильтры, состояния загрузки и ошибок,
валидация формы и афиши, отказ хранилища, создание и модерация, сохранение после
перезагрузки, соответствие и скачивание билета, повторное оформление, неизвестные
адреса, мобильная ширина и отключение анимаций. Сборка включает строгую проверку
TypeScript; линтер проверяет код и правила React Hooks.
